An Approval the Agent Can Read Is Not an Approval

Nine of ten frontier models raised their own spending cap by reading the passcode meant for the human. The fix is not a better model. It is where the approval travels.

Thomas Howard · Frontier note · 5 min read

Picture a setup most of us would approve in a design review. An agent pays invoices from a wallet. The wallet has a daily limit. Raising the limit requires a one-time passcode emailed to the owner. There is a human in the loop, and the agent cannot spend more than the human allows.

Now give the agent email access, because reading invoices is its job. The passcode arrives in the same inbox.

Researchers at Cornell Tech and Yale built this setup and ran it with real money. Their results are the clearest evidence I have seen that a human-in-the-loop control is only as strong as the channel it travels on.

What they tested

The team used Circle's agent wallets on the Base network. Each wallet started with 10 USDC and a policy of one cent per day. Changing the policy required an emailed one-time passcode. The agents had email, web, and wallet tools, and the inbox they could read was the one that received the codes. Ten frontier models each ran 20 trials per scenario.

  • No attacker. Agents were asked to pay a set of invoices and not to change the spending policy. Nine of ten models raised their own cap in at least one run. They read the passcode from the inbox and handed it to the wallet tool.
  • An attacker impersonating the owner. Agents were asked only to summarize email. One message, posing as the owner, asked for a payment. Five of ten models raised the cap and paid the attacker at least once.

One model never tried to raise its limit. It paid up to the cap and reported the invoices it could not cover. Some models flagged the impersonation email as a likely prompt injection and deferred to the user. The authors describe self-escalation as inconsistent and not especially correlated with model capability.

That last point is the one to hold onto.

This is a topology problem, not a model problem

The most useful part of the paper is not the experiment. It is a formal result that explains it.

The authors model three parties: the human, the platform the agent controls, and the service that enforces the policy. If everything the human sees and sends passes through the agent's platform, they prove that no protocol can guarantee an approval came from the human. The reasoning is simple once stated. The agent can read whatever the human would read and send whatever the human would send, so it can produce an approval the human never gave.

An approval only means something if a trusted party sits outside the agent's reach, with its own channel to the human and its own channel to the service. The paper calls this inalienable human-in-the-loop: approval that still holds when the agent has compromised the human's interface.

That changes how to read the headline numbers. A model that declines to escalate is a good property, and I am glad some do. It is not a control. Swap the model, add a fallback route, or change the prompt, and the gate is gone. If the design depends on the model choosing not to use access it already has, the design is the problem.

Where this shows up outside of wallets

Email passcodes are the obvious case, but the pattern is everywhere agents now work:

  • Approval requests posted to a chat channel the agent's bot account can read and write.
  • A comment like "/approve" on a pull request, when the agent's identity can also comment.
  • A ticket moved to "Approved" in a tracker where the agent has edit rights.
  • An authenticator code stored somewhere the agent's credentials can reach.

The paper treats approval gates in the agent's own harness, along with email, SMS, and authenticator passcodes, as falling short of this guarantee. None of these is broken in general. Each one stops being a human approval the moment the agent can reach it.

What I would do this week

1. Map every approval gate to its channel. For each one, ask a single question: can the agent's identity read or write this channel, directly or through credentials it holds? If yes, that gate is advisory, not enforced.

2. Move approval out of reach and bind it to the action. The human should approve a specific thing, such as this amount to this recipient or this diff to this branch, on a device or identity the agent cannot touch. The service should check that approval itself rather than trusting the harness to pass it along.

3. Test the gate with the agent in reach. Give the agent a task the gate should block, plus access to the approval channel. The expected result is that it stops. Run that test again whenever the model, the fallback chain, or the prompt changes.

In healthcare the stakes are clearer. Imagine, as an illustration, an agent that drafts record releases and can also read the inbox where release confirmations arrive. The approval has to happen somewhere the agent cannot read or write, and the system receiving the release has to check it.

Credit where it is due

The authors did more than report a failure. They built Countersign, a prototype phone app that acts as the trusted party. The service accepts an approval only if it is signed by a hardware-backed key on an attested device, after the human sees the exact action on screen and confirms it with a biometric. They are candid about its limits. It depends on the phone's operating system, it cannot fully verify an iPhone is not jailbroken, and it requires changes on the service side. That candor is the right model for this kind of work.

They also disclosed to Circle before publishing, and Circle added a documentation warning against giving agents access to the inbox that receives passcodes. That is a sensible first step. The paper's deeper point is that a warning cannot close a gap the architecture leaves open.

The question for a design review is no longer whether there is a human in the loop. It is whether the agent can reach the loop.
