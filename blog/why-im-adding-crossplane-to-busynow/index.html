Why I'm Adding Crossplane to BusyNow

I already have Terraform, Kubernetes, and GitOps. So why add another control plane? Because I'm trying to find out whether infrastructure can behave more like the software running on top of it.

September 2026 · Thomas Howard

BusyNow already runs on Kubernetes.

Its infrastructure is managed as code. Deployments are automated. GitOps gives me a declarative path from a repository to the cluster.

So naturally, I've decided to add another layer.

Crossplane.

That sentence should make any platform engineer at least slightly suspicious.

It makes me suspicious too.

One of the easiest ways to ruin a platform is to keep adding tools because each one solves an interesting problem in isolation. Eventually the platform becomes a collection of abstractions that requires more effort to understand than the infrastructure it was supposed to simplify.

So I'm not adding Crossplane because BusyNow desperately needs another piece of infrastructure.

I'm adding it because I'm interested in a larger question:

What happens if infrastructure becomes part of the Kubernetes control loop?

And more specifically:

Can I turn the infrastructure patterns behind BusyNow into APIs that the rest of my Engineering OS can safely consume?

That's a much more interesting experiment.

Terraform already works

The first question is obvious.

Why not just use Terraform?

I do.

Terraform is very good at what it does. I describe infrastructure, Terraform calculates the difference between the configuration and reality, and providers make the necessary changes.

For provisioning cloud infrastructure, that's an extremely useful model.

But Terraform and Kubernetes approach desired state differently.

Terraform generally runs when something invokes it.

Kubernetes continuously reconciles.

That distinction matters to me.

A Kubernetes controller doesn't look at desired state once and disappear. It keeps watching.

You say:

I want three replicas.

Kubernetes keeps asking:

Do three replicas exist?

If one disappears, Kubernetes doesn't wait for someone to run another deployment pipeline.

The control loop notices that observed state no longer matches desired state and attempts to reconcile the difference.

Crossplane takes that model and applies it to infrastructure outside the cluster.

Instead of Kubernetes only understanding things like Deployments, Services, and Jobs, it can begin reconciling cloud resources as well.

That changes the architecture in an interesting way.

Infrastructure becomes an API

Suppose I need a database for a BusyNow service.

The traditional infrastructure workflow might look something like:

Engineer → Terraform → Cloud Provider → Database

That works.

But the engineer needs to understand the infrastructure implementation; or at least interact with a workflow that does.

What I'm interested in building looks more like:

Engineer or Agent → Platform API → Crossplane → Cloud Provider

The consumer shouldn't necessarily care how the database gets created.

They should describe what they need.

Maybe someday that looks something like: 

apiVersion: platform.busynow.app/v1alpha1
kind: Database
metadata:
  name: places
spec:
  size: small
  availability: production

That's intentionally boring.

There are no subnet IDs.

No security-group configuration.

No parameter groups.

No AWS-specific instance classes.

No Terraform module arguments.

The consumer is describing intent:

Give this workload a small production database.

The platform decides what that means.

That distinction is the reason I'm interested in Crossplane.

Composition is where this gets interesting

Creating an AWS resource from Kubernetes isn't enough to justify an entire platform layer.

If all I accomplish is replacing: 

resource "aws_db_instance" "places" {
    ...
}

with a 70-line Kubernetes manifest describing the same AWS object, I've probably made the system worse.

The interesting part of Crossplane is composition.

A platform team can define a higher-level API and decide which infrastructure resources are required to satisfy it.

A Database resource might eventually cause the platform to create or configure several things:

  • the underlying database
  • networking
  • security policy
  • credentials
  • observability
  • backup configuration
  • connection information
  • ownership metadata

The application doesn't need to know how those pieces fit together.

The platform does.

Developers should consume capabilities, not infrastructure implementation details.

Crossplane gives me a way to explore what that looks like when Kubernetes itself becomes the platform API.

Why this matters for BusyNow

BusyNow is intentionally more complicated underneath than a small application strictly needs to be.

That's partly because it's a product, but it's also my platform engineering laboratory.

I don't want to learn these ideas by building architecture diagrams for fictional companies.

I want the infrastructure to have an actual job.

BusyNow gives it one.

If I create a platform abstraction incorrectly, I have to live with it.

If reconciliation behaves unexpectedly, I have to debug it.

If an abstraction leaks AWS implementation details everywhere, I have to deal with the resulting developer experience.

If adding Crossplane creates more operational burden than it removes, that's useful information too.

Production makes abstractions answer for themselves.

Crossplane and the Engineering OS

There's another reason this fits what I'm building.

My longer-term experiment with BusyNow is what I call the Engineering OS: trying to determine how much of an engineering organization can be encoded into software, agents, policy, automation, and platform infrastructure.

That creates an important problem.

AI agents can generate infrastructure code.

That's useful.

But I'm not convinced I want autonomous agents freely generating arbitrary Terraform and applying it to production.

That's an enormous authority surface.

I'd rather give automation a constrained vocabulary.

Instead of:

Create whatever AWS resources you think this feature needs.

I want something closer to:

You may request one of the infrastructure capabilities the platform exposes.

That's a very different security and governance model.

An agent might be permitted to create: 

kind: Database

without being permitted to directly manipulate RDS, IAM, VPCs, security groups, or arbitrary AWS APIs.

Crossplane potentially gives me a boundary between intent and implementation authority.

That's extremely interesting for autonomous engineering.

APIs are constraints

Platform APIs don't just make infrastructure easier to consume.

They reduce the number of things a consumer is allowed to ask for.

That's a feature.

If my platform supports three database classes: 

development
standard
production

then an application developer (or autonomous agent) doesn't need to choose among hundreds of cloud configuration options.

More importantly, it can't choose among hundreds of cloud configuration options.

I've deliberately constrained the decision space.

The platform can encode what I've already learned about networking, backups, reliability, observability, cost, and security.

Consumers operate inside those boundaries.

This is increasingly how I think about safe AI automation.

The answer isn't necessarily giving agents more intelligence. Sometimes the answer is giving them better APIs.

Crossplane doesn't replace GitOps

One architectural boundary I want to preserve is Git.

I don't want an agent talking directly to the Kubernetes API and quietly provisioning infrastructure behind my back.

The path should remain inspectable.

Something closer to:

Intent → Pull Request → Review → Git → Argo CD → Kubernetes → Crossplane → AWS

Now the request for infrastructure is an artifact.

It can be reviewed. It has history. Policy can inspect it. The Engineering OS can attach evidence to it. GitOps can determine when it enters the cluster. Crossplane reconciles it after it arrives.

Each layer has a different responsibility.

That separation matters.

Crossplane isn't replacing GitOps in this model.

It's sitting underneath it.

And it doesn't necessarily replace Terraform

I'm also not planning a dramatic "Terraform is dead" migration.

That would be solving a problem I don't have.

Some infrastructure may continue to make perfect sense in Terraform.

Foundational infrastructure in particular may remain outside the Kubernetes control plane.

The cluster itself is an obvious example.

Having the Kubernetes cluster responsible for creating the infrastructure required for the Kubernetes cluster creates some entertaining bootstrap problems.

There will probably be a boundary.

Terraform can establish foundational infrastructure.

Kubernetes and Crossplane can manage capabilities consumed through the running platform.

Where exactly that boundary belongs is something I want to learn through implementation rather than declare in advance.

The danger is abstraction for abstraction's sake

I'm enthusiastic about Crossplane.

I'm also prepared to remove it.

That's important.

Platform engineering has a tendency to produce beautiful abstractions that solve problems developers never had.

Crossplane introduces real costs.

  • Another control plane has to be operated.
  • Providers have versions.
  • CRDs have lifecycles.
  • Credentials have to be managed.
  • Reconciliation failures have to be observable.
  • Cloud APIs can behave differently from Kubernetes APIs.
  • Deletion semantics become extremely important when a Kubernetes object represents a production database.

And every abstraction I create becomes something I eventually have to maintain.

If my Database API saves thirty seconds but requires months of platform maintenance, that's not a platform improvement.

That's architecture cosplay.

The abstraction has to earn its existence.

What I'm going to build first

I'm deliberately starting small.

I don't want Crossplane managing half of BusyNow on day one.

The first implementation should prove a few basic things:

  • Can Crossplane safely manage a real cloud resource used by BusyNow?
  • Can I wrap that resource behind a simpler BusyNow-specific API?
  • Can Argo CD remain the path through which desired state enters the cluster?
  • Can I clearly observe reconciliation and failure?
  • Can I delete or change the Kubernetes resource without accidentally destroying something important?
  • Can I recover when reconciliation fails?

And most importantly:

Is the resulting system easier to reason about than what I had before?
