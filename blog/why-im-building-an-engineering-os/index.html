Why I'm Building an Engineering OS

I'm trying to find out how much of a production engineering organization can be turned into a system; and how far one engineer can take it.

September 2026 · Thomas Howard

I'm building a software company largely by myself.

That creates an obvious problem.

Building the application is only a small part of operating a real software product.

Someone has to design the architecture. Someone has to implement features, review changes, test them, deploy them, monitor production, respond to incidents, patch infrastructure, manage security, investigate failures, control costs, maintain documentation, and decide what gets built next.

Historically, those responsibilities get distributed across an engineering organization.

I don't have an engineering organization.

So I've started building one.

Not by hiring a collection of people and not by pretending that an AI coding agent is an engineering department.

I'm trying to build the organization itself as software.

I call it the Engineering OS.

The problem isn't writing enough code

AI has made producing software dramatically easier.

I can describe a feature, investigate an architecture, generate an implementation, create tests, modify Kubernetes resources, analyze failures, and work through unfamiliar code much faster than I could a few years ago.

That's incredibly powerful.

But it also exposes a misconception about software engineering.

Writing code was never the entire job.

Suppose an AI agent produces 5,000 lines of perfectly valid code while I'm asleep.

Great.

Should those changes ship?

  • Did they follow the architecture?
  • Were the right tests executed?
  • Did the implementation introduce a security problem?
  • Did it change infrastructure?
  • Does it violate an existing architectural decision?
  • What evidence proves that the change actually works?
  • What happens if production behaves differently than the test environment?
  • Who (or what) is allowed to deploy it?
  • What happens if the system gets the answer wrong?

Making implementation faster doesn't eliminate those questions.

It makes answering them more important.

What I mean by an Engineering OS

I'm not trying to build another developer portal.

I'm also not trying to create a giant prompt that says, "Run my engineering department."

The Engineering OS is the operating system around software delivery.

At a high level, I'm working toward something that looks like this:

Intent → Planning → Implementation → Review → Evidence → Deployment → Observation → Learning

Different agents and platform components can participate at different points in that lifecycle.

An implementation agent might write code. Another system can independently review the result. Automated tests can produce evidence. Policy can determine whether the evidence is sufficient. GitOps can control how an approved artifact reaches a Kubernetes cluster. Observability can determine what happened afterward. An incident workflow can react when reality doesn't match expectations.

The important part isn't that AI appears somewhere in that chain.

No single agent is the engineering organization. The system is.

Autonomy without trust isn't enough

It's tempting to measure AI engineering by how autonomous the agent is.

Can it implement a ticket without help? Can it open a pull request? Can it deploy? Can it fix production?

Those are interesting capabilities, but they're not the metric I care about most.

I care about whether I can trust the system to operate when I'm not watching it.

Those are very different things.

An agent capable of modifying production infrastructure at 3:00 AM isn't necessarily an advanced engineering system. It might just be an extremely efficient way to create an incident.

The more autonomy I add, the more interested I've become in constraints: what an agent is authorized to change, what evidence must exist before a change progresses, which actions are reversible, which decisions require human approval, and where final authority lives.

These aren't theoretical questions anymore.

They're architecture.

The goal isn't removing myself

There's an obvious interpretation of this project that I want to avoid.

I'm not trying to remove humans from engineering.

I'm trying to remove myself from work that doesn't require me.

Those aren't the same goal.

I don't need to personally watch a deployment complete successfully. I shouldn't need to manually notice that a pod is crash-looping. I don't need to repeatedly check whether a dependency is healthy. I shouldn't have to remind an engineering system that a required test suite hasn't run.

Machines are extraordinarily good at that kind of work.

What I do want to own are consequential decisions: what we build, which risks are acceptable, what architecture we're committing to, when the system should stop, when automation should require escalation, and when the evidence is insufficient.

The Engineering OS should make those decisions easier for me; not quietly make all of them on my behalf.

Why Kubernetes is part of this

A lot of what I'm building runs on Kubernetes, and that's not accidental.

Kubernetes itself is built around an idea that fits this project remarkably well:

Declare what you want, continuously observe reality, and reconcile the difference.

That model extends far beyond containers.

A deployment has a desired state. So can a release. So can a reliability requirement. So can an engineering policy. So can a synthetic check. So can evidence required before production.

I'm increasingly interested in controllers and platform APIs because they provide a way to encode operational knowledge into systems that continuously enforce it.

Documentation asks people to remember.

Platforms make the desired behavior the default.

Production is the test

The application I'm using to explore much of this is BusyNow, a real production application running on Kubernetes.

That's important because I don't want Engineering OS to become an elaborate demo.

Demos are easy to automate.

Production is where the assumptions get exposed.

Dependencies become unavailable. Networks get slow. Deployments fail. Credentials expire. Infrastructure drifts. APIs throttle requests. Agents misunderstand instructions. Tests pass while users still encounter problems.

An autonomous engineering system has to deal with that reality.

Otherwise I've just built an impressive CI pipeline.

Can one engineer really do this?

I don't know.

That's one of the reasons I'm writing about it.

My long-term question is much more interesting than whether an AI agent can implement a feature:

Can one engineer build and operate a serious software product serving thousands; (or eventually tens of thousands) of users by surrounding themselves with sufficiently capable agents, automation, and platform infrastructure?

There are obvious reasons the answer might be no. Customer support could become the bottleneck. Product decisions could become the bottleneck. Security could require specialization. Operational complexity could eventually overwhelm the system.

I don't want to assume the thesis is correct.

I want to test it.

And if the system eventually reaches a point where another engineer is required, I want to understand why.

Complexity belongs somewhere

I don't believe the goal of platform engineering should always be to eliminate complexity.

Some systems are inherently complicated. Distributed systems are complicated. Production infrastructure is complicated. Security is complicated. Reliability is complicated.

Trying to pretend otherwise often just pushes that complexity onto application developers or operators.

I'd rather concentrate complexity in the platform so that the experience of using the platform becomes simple.

The internals can be sophisticated.

The interface shouldn't have to be.

That's increasingly how I think about Engineering OS.

I may build complicated controllers, policies, evidence systems, agents, deployment workflows, and observability infrastructure underneath it.

But from my perspective as the person operating the company, the experience should eventually become much simpler:

Here's what I want.
Here's what the system did.
Here's the evidence.
Here's what requires my decision.

Everything else should increasingly disappear behind the platform.

This blog is part of the experiment

I'm going to document the project as I build it.

Not every commit and not every new tool.

I'm more interested in the engineering questions that emerge along the way.

How do you establish trust between autonomous agents? What should an AI agent actually be allowed to do in production? How do you prove that an automated engineering task was completed correctly? How should architecture constrain autonomous implementation? Where should humans remain in the control loop? Can Kubernetes controllers encode parts of an engineering organization's operating model? How do you design automation that fails safely?

And eventually:

How much engineering organization does one engineer actually need?

I expect some of my assumptions to be wrong. I expect parts of the architecture to change. I expect to build things that turn out to be unnecessary.

That's fine.

The goal isn't to prove that one person can replace an engineering organization.

The goal is to find out how much of an engineering organization can be made into a system.

And then see what becomes possible when it is.
