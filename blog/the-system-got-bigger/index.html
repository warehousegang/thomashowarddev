The System Got Bigger

Becoming CTO didn't move me away from engineering. It changed the size of the system I'm responsible for.

September 2026 · Thomas Howard

I became a CTO recently.

I expected the job to make me think less about engineering.

So far, the opposite has happened.

The system just got bigger.

As a platform engineer, I've spent a lot of time thinking about desired state.

You describe what a system should look like, observe what actually exists, and build mechanisms that continuously reconcile the difference.

I'm starting to think engineering organizations aren't entirely different.

There is a desired state: what the company needs to be able to build, operate, secure, and support.

There is an observed state: the software, architecture, people, processes, technical debt, incidents, costs, commitments, and constraints that actually exist.

And somewhere between those two is the job.

I don't mean people are Kubernetes

There's an obvious danger in this analogy.

People aren't pods.

Organizations aren't deterministic systems.

You can't write a controller that reconciles an engineer into behaving the way you want.

Nor should you try.

But the systems around people can absolutely be engineered.

That's the distinction I'm becoming increasingly interested in.

Good engineering systems should reduce the amount of organizational memory required to operate them.

Testing shouldn't depend on someone remembering to run the right suite.

Production standards shouldn't depend on someone remembering what the platform team decided six months ago.

Compliance evidence shouldn't require an archaeological expedition every time someone asks for it.

Deployment safety shouldn't depend entirely on tribal knowledge.

And AI agents shouldn't receive enormous amounts of authority simply because nobody designed better boundaries for them.

Those are engineering problems.

The code is only part of the system

Earlier in my career, the boundary around an engineering problem felt much smaller.

There was an application.

There was infrastructure.

There was a deployment system.

There were bugs to fix and features to ship.

Those things haven't disappeared.

But as CTO, the boundary now includes things I previously experienced mostly as constraints imposed on the engineering system.

  • What should we build?
  • What should we buy?
  • What shouldn't exist anymore?
  • What technical debt actually matters?
  • Where should engineers spend their time?
  • What should be automated?
  • What requires human judgment?
  • What authority should an AI agent have?
  • How do we prove that our systems are secure and compliant?
  • How much complexity can the organization afford to operate?

Those decisions eventually become architecture.

They also become cost, reliability, developer experience, product velocity, and organizational behavior.

The architecture diagram just doesn't show all of them.

Organizations accumulate manual reconciliation

Kubernetes has spoiled me in one particular way.

It made continuous reconciliation feel normal.

If I declare that three replicas should exist and one disappears, I don't want a human being checking the cluster every fifteen minutes and creating another one.

The system knows the desired state.

It observes reality.

It acts when the two diverge.

Engineering organizations contain an astonishing number of processes that work nothing like this.

Instead, we build human reconciliation loops.

Something changes → Someone notices → Someone remembers the process → Someone asks someone else → Someone updates something

Sometimes that's appropriate.

Human judgment is useful.

But sometimes we've put a person in the loop because nobody ever engineered the loop.

That's a very different thing.

This changes how I think about automation

I'm increasingly skeptical of automation whose only purpose is to make an individual task faster.

That's useful, but it's the least interesting version of automation.

I'm more interested in removing entire coordination problems.

A test suite that runs faster is good.

A system that understands when tests should run, runs them, evaluates the evidence, prevents an unsafe change from progressing, and records what happened is something different.

The first automates a task.

The second starts encoding an engineering responsibility.

The most interesting automation doesn't just save work. It removes coordination.

AI makes this question much more important

AI agents make it possible to automate engineering work that previously required judgment, not just scripting.

That's powerful.

It also creates a temptation to solve every problem by giving the agent more context, more tools, and more authority.

I don't think that's enough.

If an agent can write code, what determines whether that code is safe to merge?

If it can create infrastructure, what infrastructure is it allowed to create?

If it detects a production problem, can it change production?

If it makes a decision, what evidence should exist afterward?

Those aren't primarily prompting problems.

They're systems-design problems.

The interesting work is increasingly happening around the agent: authority boundaries, policy, evidence, observability, rollback, escalation, and interfaces.

In other words, the engineering system matters as much as the intelligence operating inside it.

This is where the Engineering OS gets more interesting

I've been building something around BusyNow that I call an Engineering OS.

The original experiment was straightforward:

How much of an engineering organization can one engineer encode into software?

BusyNow gives me a useful environment for testing that question because it's a real production system.

If the automation is bad, I have to deal with it.

If the platform is too complicated, I have to operate it.

If an abstraction doesn't work, production eventually exposes it.

Becoming CTO has given me another version of the same question.

How much organizational friction exists because responsibilities that should have been encoded into systems still depend on humans remembering to perform them?

I don't know the answer yet.

But I suspect it's a lot.

Not everything should become software

There's an important boundary here.

The goal isn't to remove humans from engineering.

Some decisions are ambiguous.

Some require context that isn't captured in a system.

Some require empathy, negotiation, creativity, or judgment.

And some decisions are important enough that a human should remain responsible even if software could technically make them.

The challenge is figuring out which is which.

I want humans spending more time on the problems that genuinely require humans.

I don't want them acting as unreliable cron jobs.

The system got bigger

My job didn't stop being engineering when I became CTO.

The boundary of what I'm engineering changed.

I'm still interested in reliable systems, good abstractions, constrained interfaces, feedback loops, observability, and making complicated things easier to operate.

It's just that now some of those systems contain software, infrastructure, AI, processes, budgets, customers, and people.

That's a much larger system.

And I think I'm going to learn a lot from trying to understand it.
