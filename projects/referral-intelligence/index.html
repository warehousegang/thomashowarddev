Building Referral Intelligence: ranking with reasons

Building production decision support at Snap eHealth: explainable physician ranking, evidence quality, and explicit recommendation policies.

Thomas Howard · 6 min read

My role
Architecture & service implementation
Focus
Python · Explainable ranking · ML data design
Project stage
Live production · Decision support

In this essay

I architect, implement, and operate Referral Intelligence, Snap eHealth’s production physician-recommendation system. It ranks specialist candidates from heterogeneous evidence, explains the factors behind each result, and withholds a recommendation when the evidence does not meet the eligibility policy.

My work spans the ranking domain, normalization, evidence adapters, eligibility rules, and service interface. The engineering challenge is making incomplete data useful while keeping the calculation, missing signals, and authority to act visible to the consuming workflow.

Separate assessment from workflow authority

The engine began inside Snap Workflows. I designed its extraction into a Python package with an authenticated FastAPI interface, separating domain contracts and scoring rules from HTTP validation and concrete adapters. The ranker consumes normalized models rather than vendor payloads or web-framework objects.

The boundary gives the assessment service one responsibility: explain the candidates. Workflows owns user sessions, operational queues, specialist selection, authorization, and EHR actions. This separation keeps a scoring change from acquiring permission to act on a referral.

The package can be verified independently of its consumer. That was a deliberate extraction decision: preserve behavior while making the scoring and API contracts easier to evolve, test, and integrate.

Make the score inspectable and repeatable

The production ranker uses explicit weights. It normalizes signals to a common scale, computes weighted contributions, and sorts by descending score with a stable provider-identifier tie-break. Factors include quality, condition experience, relevant volume, outcomes and utilization, network alignment, proximity, continuity, and evidence confidence.

Explanations come from contributions the calculation actually used. Two specialists can have similar totals for different reasons: one has an established relationship and is nearby, while another has stronger condition-specific evidence. The assessment exposes that tradeoff directly.

Explicit weights make assumptions reviewable. For example, condition experience and total volume may reflect overlapping evidence. I keep the contributions visible so that weighting decisions can be examined and revised deliberately rather than hidden inside a plausible narrative.

Preserve missingness and evidence quality

Normalization enforces the input contract. Invalid percentages, nonfinite values, negative or fractional counts, mismatched conditions, and missing provider records are rejected or represented as unavailable evidence. Network compatibility requires compatible plan information, preserving the distinction between provider identity and coverage.

Unavailable signals earn no points, and their weights are not redistributed. Coverage is returned separately. This conservative choice prevents a sparse profile from appearing complete because its few observed signals are strong. The tradeoff is that providers with less available data can score lower, so the response exposes the missing factors for review.

Confidence labels describe the available outcomes sample. Coverage describes which signals are present. Score describes the weighted assessment. Keeping those meanings separate lets the consumer explain the recommendation without presenting a ranking score as a calibrated outcome probability.

Make abstention a useful domain result

I separate ranking from eligibility. The highest-scoring candidate must still satisfy required signals, quality-profile requirements, sample-size confidence, and confirmed network compatibility. If those checks fail, the service returns the ranked assessment with reasons and withholds a recommended provider.

That is a valid decision-support result. The API distinguishes it from an authentication failure, malformed request, unknown context, or service outage so the workflow can route insufficient evidence for review.

The policy evaluates the top candidate rather than silently substituting the next person. Changing that rule would alter the recommendation policy. Stable ordering and explicit abstention make the choice visible and testable.

Verify behavior across the package boundary

Before extraction, we captured full assessment responses for six controlled synthetic scenarios. The standalone API is checked against those independent parity fixtures for ordering, contributions, coverage, confidence, missing evidence, and abstention.

Verification installs the built wheel in a separate environment, starts it outside the checkout, and exercises loopback HTTP. That catches missing package resources and accidental imports from the source directory that ordinary unit tests can miss.

API tests cover bearer authentication, invalid input, unknown contexts, cache behavior, and the distinction between abstention and a transport error. Fixture adapters are restricted to development and testing. CI runs locked package checks so the delivered package and its domain contract are verified together.

This testing strategy protects two boundaries: extraction must preserve the assessment, and the packaged service must work independently of the development checkout. A change to weights or eligibility can then be reviewed as an explicit behavior change.

Keep learned prediction explicit

The deterministic ranker assesses specialist candidates under defined rules. Predicting whether an eligible referral completes within 30 days is a separate modeling problem, with a different target, dataset, and evaluation contract.

I explore that problem in Physician Referral Success Predictor, a separate educational project. Its NumPy and pandas package generates and validates 20,000 fictional referral candidates by default. Invented relationships among wait time, distance, capacity, experience, and specialty feed a logistic simulation. Insurance acceptance is an eligibility gate: ineligible candidates have no applicable success label.

The main design decision is temporal correctness. Features must be available when a referral is created. A success becomes observable at its completion event; a non-completion becomes observable after the full 30-day window. Pending referrals remain pending, and future or same-timestamp outcomes are excluded from historical features.

The generator updates histories as outcomes become available, while validation independently recomputes them. Tests cover reproducibility, schema rules, eligibility, cold starts, and exact time boundaries. A physician with no observed history receives a neutral default and an explicit zero count.

The implemented work is the data pipeline and temporal validation. Chronological splits, fitted baselines, and probability calibration are the next modeling steps. My Fourth Down project applies related questions to historical sports data: define the outcome, enforce the prediction-time boundary, and compare against a simple baseline.

Operate an explainable decision boundary

I keep input validity, evidence coverage, ranking, eligibility, and workflow authorization separate through the service contract. Each failure has a meaningful result: reject invalid data, expose missing evidence, abstain when policy requires it, or return an explained recommendation for the authorized workflow.

That separation also makes changes reviewable. Engineers can identify whether a different recommendation came from updated evidence, a normalization rule, a weight, or an eligibility decision, then verify the affected behavior before release.
