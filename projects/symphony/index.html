Building with Symphony: from a task to a reviewable change

Architecting autonomous engineering infrastructure at Snap eHealth: scoped agents, persistent execution, and independently verifiable changes.

Thomas Howard · 8 min read

My role
Architecture & development at Snap eHealth
Focus
Codex · Symphony · Agent orchestration
Project stage
Validated local runtime · Shared service planned

In this essay

  • Task & lifecycle
  • Specialized roles

At Snap eHealth, I architect and develop autonomous engineering infrastructure around Codex and Symphony. The central problem is converting an authorized engineering task into a change that someone else can verify, without giving the agent unrestricted authority over the repository, credentials, or release process.

OpenAI’s upstream Symphony specification provides the scheduler and runner foundation: issue intake, per-issue workspaces, agent sessions, retries, and reconciliation. My work is the Snap-specific architecture around that foundation: admission policy, repository context, specialized work, execution boundaries, durable state, and evidence for review. I did not create the upstream specification.

Current maturity: a bounded synthetic execution milestone has passed. A newer local orchestration implementation supports persistent sessions and test-repair loops and remains under review. Shared, always-on dispatch and the complete autonomous delivery handoff are still separate acceptance milestones.

An executable task needs an authorization contract

A useful task identifies one repository, a source revision, allowed changes, acceptance criteria, test commands, and a human reviewer. Repository guidance and relevant architecture explain how to work within that scope. Neither a ticket’s prose nor an agent’s own plan can grant new permissions. A Linear candidate label requests consideration; it is not execution approval.

The newer controller accepts a plan bound to its recorded human decision. The plan defines task dependencies, permitted write paths, tests, and finite execution limits. Ordinary test failures can trigger repairs within that approval and remaining budget. A changed scope, revoked decision, or exhausted limit is a different event and must stop execution.

Specialized agents need explicit handoffs

I use specialization to separate questions that an implementation session can otherwise conflate: does the code satisfy the task, do the tests challenge it, and is the change safe to accept? These role contracts describe the workflow I am developing, not a continuously operating fleet of ten production agents.

Implementation
Receives the approved task, repository context, and write scope. Produces a candidate diff and developer checks; cannot change its authority or declare independent acceptance.
Testing / QA
Receives acceptance criteria and the candidate. Adds or runs permitted tests, exercises failure cases, and returns reproducible results and coverage gaps.
Review
Inspects the exact diff, requirements, and evidence. Returns findings and unresolved risks. A review is not permission to silently rewrite the candidate it evaluated.
Debugging
Starts from a failing check, bounded diagnostics, and retained state. Reproduces the failure and proposes a targeted correction within the approved scope.
Security
Examines permissions, credentials, data flows, and trust boundaries. Returns findings and required controls; agent review cannot substitute for human risk acceptance.
Remediation
Receives a specific finding or failed test. Repairs permitted files and returns a new candidate for verification. Earlier passing evidence cannot approve changed artifacts.

The reviewed controller has frontend, backend, QA, SRE, security, and delivery task labels. It runs dependency-ordered tasks serially, with a persisted Codex session for each task. Debugging and remediation can continue within that session. Independent review remains a separate responsibility; role names alone do not create independence or enforce permissions.

Runtime boundaries must survive model mistakes

Scope the worker, then isolate validation

The newer local runtime uses native Codex filesystem and network permissions, disables external apps, plugins, and MCP servers, and checks that the returned session matches the requested workspace and permission profile. Authentication stays managed by Codex. This is a different execution path from the earlier container worker with a host-only model relay; I do not treat their security properties as interchangeable.

Validation runs separately in a pinned, nonroot container with no network, bounded resources, and a read-only source export. Git metadata, approval records, the journal, and host credentials are excluded. Repository context helps the agent choose the right implementation; operating-system permissions and host checks determine what it can actually do. A prompt asking for restraint is not an isolation boundary.

Make authority expire and stale work fail

The earlier broker implementation includes signed execution leases. A host verifies a separately signed approval, binds the lease to its task and worker, and checks an expiry and persisted generation. Revocation or supersession advances that generation, so an old signed lease no longer authorizes a request. This is fencing: a valid old signature cannot override the current authority record.

The newer local controller instead binds its journal to the approved plan, checks cancellation and expiry, and reconciles worker identity before resuming interrupted work. Out-of-scope changes quarantine the run for inspection. These are implemented controls on their respective paths; they are not evidence that a shared Linear dispatcher already coordinates distributed leases. The control-plane essay develops that broader design.

Budget uncertainty is state, not spare capacity

Time, turn, token, process, and memory limits constrain different failure modes. Durable reservations prevent a restart from making uncertain work look free. In the broker path, requests reserve against configured cost bounds before forwarding; missing terminal usage leaves a hold for reconciliation. In the newer subscription-backed path, observed usage thresholds can stop further work, but an in-flight request can overshoot them.

Neither a socket close nor a local timeout proves that provider computation or billing stopped. The journal retains uncertain reservations, and account-wide allowance changes are not attributed to one task. These controls bound local execution and scheduling; they do not establish a provider-enforced dollar cap or measured cost savings.

Verify the change, not the agent’s confidence

Task acceptance starts with explicit expected behavior. Developer tests and a successful model turn are useful evidence, but neither alone establishes delivery. The candidate must stay within scope, pass deterministic checks, and retain an identity that downstream CI and reviewers can match to the actual diff.

The local controller checks the workspace before and after validation and re-runs the combined test suite before requesting delivery. If a final check fails, it returns the responsible task to a bounded repair loop. Changed artifacts invalidate earlier validation. A role’s “passed” message cannot replace the test process result or become an authoritative CI check.

The reviewed orchestration module has 57 offline regression tests, independently rerun for this essay. They cover persisted cancellation, interrupted-work recovery, retained unknown usage, scope quarantine, stale test evidence, final-suite repair, and ambiguous publication outcomes. These tests use controlled fixtures and local processes; they are not 57 successful autonomous production tasks.

Publication is also a protocol. The implementation under review records delivery intent before an external mutation and requires a separate readback of remote identity, parent revision, and artifact contents before acknowledging success. If the result is uncertain, it reconciles instead of blindly repeating the write. The current adapter targets an existing open draft PR; complete live connector delivery remains unproven. An acknowledged delivery request still leaves independent checks and human review pending.

Debugging changed the acceptance standard

An early package check built the runtime and initialized Codex while its inner command sandbox still reported a missing capability. That was evidence of startup, not useful task execution. Later offline tests exercised the real pinned process against a synthetic provider, including file creation, command execution, and matching completion events. The acceptance standard became an observable task outcome under the intended restrictions.

A failed live attempt also exposed a diagnostic weakness: the worker returned a generic error, discarded stderr, and was removed before useful failure evidence survived. Offline reproduction found request-policy incompatibilities, but could not recover the exact historical exception. The correction preserves bounded, sanitized failure categories and container state before cleanup. Evidence retention became part of the runtime contract, without exporting raw prompts, credentials, or arbitrary tool output.

The newer local path encountered a different boundary: its strict native filesystem profile denied the host’s Python framework. The solution was to keep editing scoped and move tests to the isolated host validator. Broadening worker access simply to make the first test command succeed would have changed the security contract instead of resolving the integration.

Validated local execution; shared operation still ahead

The first bounded synthetic acceptance completed a real model turn, produced the expected code, and passed tests rerun in a fresh isolated container. Its recorded approval was operator self-authorization for that experiment, not independent human security attestation. Later local acceptance exercised managed Codex sessions, generated regression tests, validated them in Docker, and resumed persisted state. That run retained delivery requests; it did not publish a task PR.

The signed broker controls are in the canonical repository. The newer persistent orchestration and connected-delivery implementation remains in an open review branch. Automatic shared intake is disabled; unattended connector operation, full QA integration, shared-host commissioning, and live recovery during an in-flight model turn still need acceptance evidence. Human-controlled merge and deployment remain required.

My architectural focus is the chain between those milestones: authorized work, bounded execution, inspectable evidence, and an explicit acceptance decision. The useful unit of progress is a change another engineer can verify, with its limits still visible.
