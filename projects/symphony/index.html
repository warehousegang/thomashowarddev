Building with Symphony: from a task to a reviewable change

How I approach agent context, specialized roles, bounded execution, and evidence in engineering workflows built around Codex and Symphony.

Thomas Howard · 5 min read

Project stage

In this essay

A coding agent can make a useful change while leaving a surprisingly difficult coordination problem behind it. Which version of the repository did it use? What was it allowed to change? Can another agent reproduce its result? Who decides that the work is ready to merge?

My work with Codex and Symphony at Snap eHealth starts with those questions. I have been developing workflows for specialized engineering agents across implementation, testing, review, debugging, and remediation. The goal is to turn a bounded engineering request into a reviewable result whose scope and evidence are easy to understand.

Symphony originates with OpenAI’s open-source specification. Our project adapts that foundation to Snap’s work intake, execution constraints, and review process. The work described here includes a local single-ticket harness and a prepared shared-service runtime. The shared automatic dispatcher is not active.

Start with a task that can be completed

We designed intake around a human-selected, bounded work item. It identifies one repository, describes the intended change, and supplies acceptance criteria. A broad instruction such as “improve this application” leaves too many decisions implicit for an unattended worker. A specific defect, its expected behavior, and the relevant verification give the agent a much more useful starting point.

A candidate label expresses interest in running the work; it does not grant execution authority. The admission design separately considers source and policy versions, budget, reviewer, and whether the service has been placed on hold. This separates the business request from the operational decision to execute it.

The context supplied to an agent is part of the solution. Repository guidance, known constraints, test commands, and relevant architecture need to be discoverable. The aim is to give a worker enough information to act independently without asking it to reconstruct the organization from a directory of source files.

Specialization makes the handoffs explicit

The engineering workflow uses specialized roles because implementation, testing, and review ask different questions. An implementation agent is trying to satisfy a requirement. A reviewer is looking for mistakes, missing cases, and unintended consequences. A debugging agent needs to investigate a failure before proposing another patch.

My broader agent work has involved ten specialized engineering agents. The meaningful design choice is what each role can see, change, and return. A review that silently rewrites the implementation makes it harder to understand what was evaluated. A test agent that reports only “passed” leaves the next person without a reproducible basis for confidence.

The handoff therefore needs an artifact and its evidence: a candidate change, the checks performed, unresolved findings, and enough context for the next role to continue. Adding more agents helps only when their responsibilities and exchanges reduce ambiguity. Otherwise, it creates more coordination work.

Execution and publication are separate capabilities

We designed the worker to operate inside a bounded environment. The prepared runtime package combines pinned Symphony and Codex components with restricted container checks. Those checks inspect the actual configuration: network access, filesystem mounts, user privileges, resource limits, and deadlines. A declared configuration is useful, but the running environment is what determines the worker’s effective capabilities.

Publication is a separate responsibility. The shared-service design uses a constrained publisher to create a pull request, followed by independent CI and human review. Workers do not approve their own work, merge protected branches, or deploy a result. This makes it possible to give an agent room to investigate and test while keeping the acceptance of its output explicit.

Cancellation also requires more than stopping the most visible process. The design needs a durable stop state and a way to prevent stale work from being accepted after authority changes. In my earlier control-plane essay, I examine leases, fencing, and reconciliation in more detail. Here, those concerns are acceptance requirements for the shared service, not claims that every part is already commissioned.

A runtime package is a useful, limited milestone

Preparing the runtime gave us a concrete artifact to inspect and test. The recorded checks built a native ARM64 image, ran selected upstream tests, and completed the Codex initialization handshake inside a restricted container. They did not send a model prompt or launch a live shared dispatcher.

That distinction exposed an important integration issue: initialization could succeed while the inner command sandbox still lacked a capability it expected. Treating the handshake as proof of end-to-end execution would have hidden the remaining work. The useful result was a narrower one: the package could be built and initialized, while live command execution still needed its intended boundary resolved and tested.

Our verification approach separates several questions. Does the package build? Can a worker initialize? Can it execute a bounded task under the intended restrictions? Can it be stopped and recovered? Can the accepted result reach review without giving the worker additional authority? Each question requires its own evidence.

From a local harness to a shared service

The project currently has a local single-ticket foundation, a prepared runtime package, and a defined shared-service workflow. Shared-host commissioning, portable admission and stop handling, budget integration, and the full publication handoff remain part of the next stage. The preparation repository keeps automatic execution disabled.

That is a substantial architecture project in its own right: taking an interaction that works for one engineer and making its assumptions explicit enough for a team to operate. The important outcome is a path from an authorized task to a candidate change with evidence. Agent count and generated code volume are secondary to whether someone else can understand, verify, and safely accept the result.
