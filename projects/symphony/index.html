Building with Symphony: from a task to a reviewable change

Architecting autonomous engineering infrastructure at Snap eHealth: scoped agents, persistent execution, and independently verifiable changes.

Thomas Howard · 6 min read

My role
Architecture & development at Snap eHealth
Focus
Codex · Symphony · Agent orchestration
Project stage
Live production · Agentic engineering

In this essay

  • Task & lifecycle
  • Specialized roles
  • Execution boundaries
  • Verification
  • Debugging lessons
  • Operating the system

I architect, build, and operate Symphony-based autonomous engineering infrastructure for Snap eHealth’s production workflows. It converts authorized engineering tasks into reviewable changes through scoped execution, specialized agents, deterministic verification, and human-controlled release.

OpenAI’s upstream Symphony specification supplies the scheduler and runner foundation: issue intake, per-issue workspaces, sessions, retries, and reconciliation. My contribution is Snap’s application of that foundation: admission policy, repository context, execution boundaries, durable orchestration, and evidence for acceptance.

The engineering problem is preserving useful autonomy inside a precise authorization contract. Agents need enough freedom to investigate and repair code. The runtime must keep that work within the approved repository, scope, budget, and release process.

Turn a task into an executable contract

A task identifies its repository and source revision, allowed changes, acceptance criteria, test commands, and reviewer. Repository guidance supplies implementation context. Admission checks bind the work to a recorded human decision; a ticket label or agent-generated plan cannot grant additional authority.

I built a persistent controller extension that records dependencies, permitted write paths, tests, and finite execution limits. Failed tests can trigger repairs inside the approval and remaining budget. Changed scope, revoked authority, expired approval, and exhausted limits stop execution.

Coordinate specialized work through explicit handoffs

I separate implementation, testing, and acceptance so that each role has a concrete input, permitted action, and output. The same task may move through several roles as evidence develops.

Implementation
Receives the approved task, repository context, and write scope. Produces a candidate diff and developer checks within that scope.
Testing / QA
Receives acceptance criteria and the candidate. Adds or runs permitted tests and returns reproducible results and coverage gaps.
Review
Inspects the exact diff, requirements, and verification evidence. Returns findings and unresolved risks while preserving the reviewed candidate.
Debugging
Uses a failed check, bounded diagnostics, and retained state to reproduce the problem and identify a targeted correction.
Security
Examines permissions, credentials, data flows, and trust boundaries. Returns findings and required controls for the acceptance decision.
Remediation
Repairs an identified defect within permitted files and submits the changed candidate for fresh verification.

The controller orders dependent tasks serially and persists a Codex session for each task. Debugging and remediation can continue within that session. Independent review runs outside the implementation session, with its own evidence and authority boundary.

Enforce boundaries in the runtime

Scope editing and isolate validation

The native Codex controller applies filesystem and network permissions, disables external apps, plugins, and MCP servers, and checks the returned workspace and permission profile. Codex manages authentication. The broker path instead uses a container worker and a host-only model relay; each path has explicit controls for its execution model.

Validation runs in a pinned, nonroot container with no network, bounded resources, and a read-only source export. The export excludes Git metadata, approval records, the journal, and host credentials. Repository context guides the work; operating-system permissions and host checks enforce access.

Expire authority and reject stale work

The broker uses signed execution leases bound to a separately signed approval, task, worker, expiry, and persisted generation. Revocation advances that generation. A previously valid signature then fails the current authority check, fencing off stale work.

The persistent controller binds its journal to the approved plan, checks cancellation and expiry, and reconciles worker identity before resuming. Out-of-scope changes quarantine the run for inspection. My control-plane essay develops the architecture behind those decisions.

Retain uncertain usage across restarts

Time, turn, token, process, and memory limits constrain different failure modes. Broker requests reserve against configured cost bounds before forwarding. Missing terminal usage leaves a durable hold for reconciliation, preventing a restart from making uncertain work look free.

In the subscription-backed controller, observed usage thresholds stop further work; an in-flight request can exceed a threshold. Provider work can also outlast a local timeout. The journal retains those uncertainties instead of treating cancellation as proof of unused capacity.

Bind acceptance to the exact candidate

The controller checks workspace scope before and after validation and reruns the combined suite before requesting delivery. A final failure returns the responsible task to a bounded repair loop. Any artifact change invalidates earlier passing evidence.

The orchestration module’s 57 passing regression tests cover persisted cancellation, interrupted-work recovery, unknown usage, scope quarantine, stale test evidence, final-suite repair, and ambiguous publication outcomes. Controlled fixtures and local processes make those failure paths reproducible.

I implemented publication as a recoverable protocol: persist delivery intent before a write, then read back the remote identity, parent revision, and artifact contents. An uncertain result triggers reconciliation rather than a blind retry. The adapter targets an existing draft PR and leaves merge authority with the reviewer.

Snap Workflows supplies an independent hosted verification path: canonical CI followed by architecture review. The reviewer receives the candidate and evidence through read-only mounts, runs without host credentials, and uses a constrained inference proxy. Its result must match the candidate revision and successful checks. Human approval controls merging and deployment.

Use failures to improve the execution contract

An early runtime check initialized Codex successfully while command execution still lacked a required sandbox capability. I tightened acceptance around an observable outcome: create the expected file, execute the command under the intended restrictions, and retain matching completion events.

A failed model attempt exposed another gap: generic errors and premature cleanup removed useful diagnostic evidence. The correction retained bounded failure categories and container state before cleanup while excluding raw prompts and credentials.

When native filesystem restrictions blocked the host’s Python framework, I kept editing scoped and moved tests to the isolated validator. The failure improved the separation between implementation and verification instead of expanding worker access.

Operate around explicit acceptance decisions

I treat the task, its authority, the candidate, and its verification as one operational record. That record explains whether work may continue, why it stopped, and what a reviewer is accepting. Human authorization remains part of the architecture throughout implementation, recovery, and release.
