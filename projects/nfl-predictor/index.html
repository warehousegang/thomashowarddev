Building NFL Predictor: from historical games to win probabilities

How I’m approaching predictive modeling with historical NFL data, pregame features, simple baselines, and evaluation across later seasons.

I'm building NFL Predictor as an independent predictive machine learning project. The first question is specific: using information available before kickoff, how can we estimate the probability that the designated home team wins? Football gives me a domain I enjoy and a concrete way to examine how data preparation, model choices, and evaluation affect a forecast.

The project starts with historical game data and simple benchmarks. The longer-term design adds richer team features, a prediction service, and an agent that can investigate a forecast. The current implementation is the data-exploration script; baseline evaluation and model training are the next milestones.

Start with real games and a precise target

The exploration script uses nflreadpy to request nflverse schedules and results for the 2010–2025 seasons, then converts the returned data into a pandas DataFrame. It keeps completed regular-season games, requires both scores, and creates a binary home-win label. It also prints the game count, season count, overall home-win rate, and a small sample for inspection.

For the initial binary experiment, tied games are excluded. That choice defines the population the model will learn from: completed regular-season games with a decisive result. A future live forecast needs an explicit policy for ties, and playoff games need their own evaluation before the results can be generalized to them. Those boundaries belong in the experiment record.

The scores establish what happened. They cannot become inputs for predicting the same game. Similarly, the home-win rate printed across the exploration dataset is descriptive; the probability used by the benchmark must be estimated from training seasons alone.

Give the model a benchmark to beat

The first baseline makes the same classification for every game: the home team wins. Its accuracy provides a reference for winner selection. A second baseline assigns every matchup the home-win frequency observed in the training data. That gives us a probability forecast we can score against later outcomes.

These baselines answer different questions. A fixed winner choice does not say how likely that outcome is. A fixed probability can be evaluated for probability quality even though it never distinguishes one matchup from another. Keeping both makes it easier to see what a trained model actually contributes.

The initial evaluation plan uses 2010–2022 for training, 2023 for validation, and 2024–2025 for the final historical comparison. Model selection belongs in the validation period. The final test period is reserved for evaluating the selected approach, rather than repeatedly choosing features based on those results.

Reconstruct what was known before kickoff

A historical table is assembled after the games have happened. It can contain information that would have been unavailable when a forecast was needed. That makes the prediction timestamp a central design decision.

For a Week 8 matchup, a team's scoring average from completed Weeks 1–7 can be a candidate feature. Its average across the entire season includes the game being predicted and subsequent games. Using that value would let future outcomes influence the forecast. Sorting the train and test sets chronologically would not repair the contaminated feature.

The planned feature pipeline therefore calculates team history strictly from earlier completed games. Rolling statistics must be shifted so the current game cannot contribute to its own inputs. Season openers and teams with little recent history also need explicit defaults or prior-season information, with those choices recorded and evaluated.

Learned preprocessing needs the same separation. Any imputation, scaling, or feature selection fitted from data must learn from the training portion and then be applied to validation and test data. The scikit-learn guidance on leakage is useful here: wrapping transformations in a pipeline helps maintain that boundary, but the engineering still has to enforce when each raw feature became available.

Use logistic regression to make the first experiment understandable

The planned first trained model is logistic regression in scikit-learn. The initial features focus on differences between the two teams' pregame win percentages and scoring margins. Starting with a small feature set makes it possible to trace a result back through the calculation and investigate whether an apparent improvement comes from useful information or a mistake in the data.

Because each row is already expressed from the home team's perspective, a constant “is home” flag would not distinguish games. The intercept can capture a baseline tendency, while differences in team history provide matchup-specific information. Neutral-site handling is another condition to examine before interpreting that tendency as ordinary home-field advantage.

Later experiments may add rolling statistics, Elo ratings, rest days, and opponent strength, then compare gradient boosting with the simpler model. Each addition needs an out-of-time comparison against the same baselines. A coefficient or feature importance can describe a model's behavior; it does not by itself establish why a team wins.

Evaluate the probability as well as the pick

Accuracy measures winner selection at a chosen threshold. For probability forecasts, the plan also includes Brier score, the average squared difference between forecast probabilities and binary outcomes, and log loss, which strongly penalizes confident errors. Those measures make it possible to distinguish models that select similar winners but assign very different probabilities.

I also want calibration curves with the number of games supporting each probability range. Across enough comparable forecasts near 70%, roughly seven in ten should be wins if those probabilities are well calibrated. A lower aggregate Brier score alone does not prove better calibration, and small groups can produce noisy estimates.

The evaluation should report results by season as well as across the full holdout. It should retain the data snapshot, filtering rules, feature definitions, and model configuration needed to reproduce the comparison. The project does not yet have measured model-performance results; publishing those results belongs after the baseline and training milestones have actually run.

Let an agent investigate a forecast

The longer-term product design includes an NFL analyst that can retrieve supporting information, call the prediction model, and explain a result. The trained model would supply the probability. The agent would identify the model version, summarize the available evidence, and make the assumptions visible.

Scenario analysis needs that boundary too. If a later model supports a player-availability input, a tool could change that input and rerun inference. Until the feature exists and has been evaluated, an agent should not invent a revised probability because an injury sounds consequential. A plausible football explanation is not a substitute for a measured predictive calculation.

The API, dashboard, and research agent remain later milestones. My immediate focus is the foundation: a defensible target, historical information available at prediction time, simple benchmarks, and an evaluation that tells me whether the next modeling decision helped.

The connection to referral prediction

This project complements my separate work on 30-day referral-completion modeling. That project starts with a reproducible synthetic data generator and tests for when prior outcomes become observable. NFL Predictor uses historical sports records. Both require a clear distinction between an outcome we know today and information that was available when the prediction would have been made.

That is the predictive modeling experience I want to develop and document: framing the question, constructing the dataset, engineering valid features, comparing models, and examining uncertainty before putting a forecast into a larger AI workflow.
