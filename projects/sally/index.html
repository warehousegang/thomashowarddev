Building Sally: conversation, context, and a trustworthy visit brief

How we separated real-time conversation, background analysis, and evidence-backed extraction in a healthcare voice agent.

October 23, 2026 · Thomas Howard · 5 min read

My role
Applied AI architecture & development
Focus
TypeScript · Voice · Structured outputs
Project stage
Restricted synthetic prototype

In this essay

  • Three workloads
  • Background context
  • Action evidence
  • Evaluation lessons
  • Current status

A voice agent has very little room to hide a poor architectural decision. The caller experiences a slow model as silence, a stale response as an interruption, and an unsupported claim as a broken promise. Sally brought those problems together in one product: a healthcare voice agent that can hold a conversation, use tools, and turn what it learns into a structured visit brief.

I lead Sally’s applied AI architecture and development at Snap eHealth. The work spans the conversation itself, the tools available to it, the background analysis, and the evidence used to check the resulting brief. The central design problem has been deciding which work belongs in the caller’s immediate experience and which work can happen alongside it.

Three workloads with different deadlines

We separated Sally into a fast conversation loop, a slower analysis loop, and a final extraction step. Each has a different output and a different tolerance for waiting. The conversation loop needs to respond to the person. Background analysis needs to retain useful context. Final extraction needs to produce an accurate account of the completed conversation.

That separation lets us make different choices for each workload. A model that produces a thoughtful analysis may still be a poor choice for the speaking role if callers wait too long between turns. Conversely, the fastest speaker is not automatically the best model for extracting a careful record. We evaluate those responsibilities separately.

The implementation uses TypeScript, with shared conversation logic behind browser and phone transports. Retell handles the live audio session and Twilio supplies the telephone route. Our application owns the conversation and its state. Keeping that ownership clear gives us one place to evolve prompts, tools, and extraction behavior instead of maintaining a separate agent for every channel.

Keeping analysis off the conversation path

Moving analysis into the background sounds straightforward until a person corrects themselves while that analysis is running. A result can be valid for an earlier transcript and already be stale when it returns. Applying it blindly would let old context overwrite newer information.

We built and tested the separation around those timing problems. Background work can be coalesced, and stale revisions are rejected. A regression test holds the slow provider response open while the conversation completes its speech path, then checks how the later update is handled. That proves an architectural property: routine background work does not have to finish before Sally responds.

It does not prove how quickly a caller hears audio over a real phone connection. Provider inference, transport, synthesis, and playback contribute their own delay. Keeping those measurements separate helps us improve the part of the system responsible for a problem.

A spoken promise needs an actual result

Tool use introduces another kind of timing problem. A model can generate a sentence that assumes an action succeeded before the tool has confirmed it. In an appointment scenario, “you’re booked” is a consequential claim. A fluent sentence is insufficient evidence that anything was booked.

We treat tool results as a separate source of truth. The final brief is checked against action evidence as well as the conversation. A booking claim in a transcript cannot substitute for a successful function result. Patient statements also need evidence: extraction validation checks references and quotations, and it rejects unsupported claims of chart verification when no chart integration exists.

The same principle applies when a response is interrupted or a session closes. An earlier model response must not continue causing tool effects simply because its request eventually completes. Tests cover response identity, closed-session state, and disabled-call gates so delayed work does not inherit authority from an obsolete turn.

What the evaluations taught us

We use deterministic tests to check state transitions and evidence handling, then separate provider screens to examine behavior with actual models. One useful technique is replaying a fixed caller turn against multiple candidates. The conversation history stays fixed up to that point, and each candidate supplies the next response.

This avoids a misleading comparison. Once a different model says something different, the caller might answer differently too. Replaying the original caller’s later words as if nothing changed would no longer be the same conversation. A fixed-turn comparison answers a narrower, more defensible question.

Some of the most useful findings were defects in the surrounding instructions and evaluator. An unavailable-slot scenario exposed a missing statement that the offered slots represented the complete availability. Correcting that context was more appropriate than rewriting the speaking model’s personality. Another screen progressed through a synthetic conversation so quickly that background analysis could not arrive in time; its result partly rewarded a slower speech path. Making turn pacing explicit helped separate a test artifact from a product regression.

These investigations changed how I approach model selection. I want to know which behavior failed, what information the model actually received, and whether the test represents the workload. A larger model or a longer prompt is only useful if it addresses the demonstrated cause.

What is implemented, and what comes next

Sally has implemented conversation, analysis, extraction, transport, and validation components, alongside a synthetic scheduling demonstration. The scheduling presentation uses prerecorded dialogue; it does not book appointments. The interactive application is also restricted to approved synthetic demonstrations.

The current source requires AI disclosure and recipient verification before protected context, model conversation, or actions. With no production verification adapter installed, that gate permits only a neutral introduction and safe termination. Live EHR connectivity and production scheduling remain separate integration work. Earlier prototype and provider-test results establish specific capabilities; they do not establish a production healthcare deployment.

The work has given me a concrete way to reason about conversational AI: separate the workloads by their deadlines, preserve the distinction between statements and completed actions, and evaluate each boundary with evidence that actually exercises it. That is how an engaging conversation becomes part of a dependable application.
