Building Sally: conversation, context, and a trustworthy visit brief

Leading Applied AI architecture and development at Snap eHealth: real-time conversation, evidence-checked visit briefs, and the evaluations behind them.

I lead the architecture, development, and operation of Sally, Snap eHealth’s production conversational AI system. Sally combines real-time healthcare conversation, controlled tool execution, and structured visit briefs. I own the engineering decisions that connect the voice experience to persistent state, background analysis, evidence processing, and reliable releases.

The central challenge is coordinating three kinds of authority: what the model may say, what the application may do, and what the resulting record can support. A caller experiences a slow response as silence, stale context as a repeated question, and an unsupported action claim as a broken promise.

Three workloads, different deadlines

I separated the fast conversation loop, background analysis, and final extraction. The speaker handles the current turn using accepted context. Analysis maintains that context alongside the conversation. Extraction produces a visit brief from the completed transcript and recorded actions.

The TypeScript runtime shares conversation logic across phone and browser transports. Retell handles the audio session; Twilio supplies the telephone route. Sally owns prompts, state, tools, and extraction. Keeping transport adapters separate from application policy lets the runtime enforce the same authorization rules across entry points.

This separation also guides model selection. The speaking model needs responsive turn-taking; analysis needs useful context; extraction needs precise structured output. I evaluate each role against its own deadline and behavior contract.

Accept background context without stale overwrites

A caller can correct themselves while analysis is running. I designed the context path to coalesce work and validate each result against the transcript snapshot it read. New turns may extend an unchanged prefix. Rewritten source turns, removed evidence, or a result that would rewind processed progress cause rejection.

Accepted context is committed for later turns, keeping analysis off the routine speech path. A regression test holds the analysis response open while speech completes, directly protecting that separation. Inference, transport, synthesis, and playback remain distinct parts of the latency budget.

Operate durable state and controlled releases

The AWS runtime uses a Node backend behind an HTTPS load balancer, ECS Fargate, and private PostgreSQL storage. An actor abstraction retains the conversation handlers while storing state and scheduled work in the database. State changes and alarms commit together. Interrupted alarms can retry; uncertain call-creation attempts enter reconciliation to prevent duplicate calls.

A database advisory lock enforces one active process. If its connection is lost, the runtime removes readiness, stops scheduling, and closes WebSockets. This makes ownership explicit. The operational tradeoff is drained deployment: durable records support recovery, while active calls must be drained before process replacement.

The release workflow builds an immutable staging image and promotes the same tested digest to production. Call draining and readiness checks govern replacement; calling authorization remains an independent gate. Operational logs contain metadata, while conversation artifacts have a separate access boundary.

I also built a finalized-call delivery path with a transactional outbox, queue processing, private artifact storage, and retried callbacks. Persisting delivery intent alongside state makes temporary downstream failures recoverable and duplicate events manageable.

Make actions depend on committed results

For booking and availability tool requests, the fast loop withholds draft speech, executes through the runtime, and asks the model to respond using the committed result. The extra model round is a deliberate tradeoff: action evidence arrives before the application speaks about the outcome.

Before applying an effect, the executor rechecks the active socket, response identity, session state, calling gate, and recipient authorization. A response from an interrupted turn loses authority. Disclosure, consent, and recipient verification are application policies; an instruction in the conversation cannot replace them. When verification is unavailable, the runtime fails closed.

Final extraction applies another set of deterministic checks. A confirmed booking requires a successful tool result. Structured output must satisfy its schema, transcript references must resolve, and quotations must match their cited turns. Chart context retains its source identity instead of being silently promoted into verified conversation evidence.

Evaluate timing, behavior, and evidence

Reproduce failures at the boundary

Provider-stubbed tests control timing and outputs. They exercise speech while analysis is pending, stale context, delayed tool requests after interruption or reconnect, closed sessions, and disabled calling. Extraction tests inject bad references, drifting quotations, and transcripts that claim a booking without a successful tool result.

Live-model scenarios cover unavailable appointments, caller-selected slots, instruction overrides, AI disclosure, and conversational continuity. Tool assertions and behavioral rubrics keep failures inspectable as prompts, adapters, and models change. Controlled synthetic cases give the tests repeatable inputs without using patient records.

Compare models at a stable decision point

For speaking-model comparisons, I freeze the conversation at one caller turn and ask each candidate for its next response. That holds the input constant. I avoid replaying an entire original conversation after a candidate diverges, because the caller’s subsequent response would also change.

Debug the evaluator as carefully as the model

One unavailable-slot failure came from incomplete booking context: the model had not been told that the offered slots were the full availability for that call. Clarifying that context corrected the test without changing the speaking prompt.

Another screen advanced so quickly that background analysis arrived after the scored turns. I made turn pacing and accepted-memory arrival explicit. Blocking speech on analysis would have hidden the measurement defect while damaging the latency design.

The continuity reports preserve scenario identifiers, source and prompt hashes, provider rounds, speech, tool activity, timing spans, and mechanical failures. Separating mechanical checks from semantic review helps me decide whether to change the application, its context, the evaluator, or the model.

Produce a record the care team can inspect

A useful visit brief preserves the difference between a patient statement, supplied chart context, consent, and a completed action. Background context supports continuity during the call; transcript references and committed tool results make the resulting record traceable afterward.

Own the system through operation

My responsibility spans model behavior, runtime state, transport integration, deployment, and evaluation. When a failure crosses those boundaries, I trace it through the recorded turn, accepted context, tool result, and extraction evidence. That structure makes an incident actionable and turns the correction into a targeted regression test.
