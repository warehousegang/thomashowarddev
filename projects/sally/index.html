Building Sally: conversation, context, and a trustworthy visit brief

Leading Applied AI architecture and development at Snap eHealth: real-time conversation, evidence-checked visit briefs, and the evaluations behind them.

I lead Sally’s Applied AI architecture and development for Snap eHealth’s production workflows. Sally brings together real-time healthcare conversation, bounded tool execution, and structured visit briefs. My work connects LLM orchestration and persistent conversational state with background analysis, evidence-checked extraction, evaluation, and runtime reliability.

The engineering problem is deciding what the model may say, what the application may do, and what evidence can support the resulting record. A caller experiences a slow response as silence, stale context as a repeated question, and an unsupported action claim as a broken promise. Healthcare adds consent and authorization boundaries that fluent conversation cannot replace.

The production engineering problem extends beyond the conversation: state must survive process failure, delayed work must not acquire fresh authority, and a release must preserve the boundary between speaking, acting, and recording evidence. I use controlled synthetic scenarios to test those properties without treating test activity as proof of a live healthcare integration.

Real-time orchestration: three workloads, different deadlines

The architectural decision at the center of my work is to separate the fast conversation loop, slower background analysis, and final extraction. The speaker handles the current turn. Analysis maintains useful context alongside the conversation. Extraction works from the completed transcript and action evidence to produce the visit brief.

The TypeScript runtime shares conversation logic across phone and browser transports. Retell handles the live audio session; Twilio supplies the telephone route. Sally owns conversation state, prompts, tool execution, and extraction. Transport adapters and the application’s authority checks remain separate, so receiving an audio session does not itself authorize protected context or an action.

Separating the workloads also separates model choices. A model that produces careful analysis may be unsuitable for the speaking role if callers wait too long. The fastest speaker is not automatically the best extractor. Each role needs evidence appropriate to its deadline and output.

Background context without stale overwrites

A person can correct themselves while analysis is still running. The returned result may describe a valid earlier transcript but no longer fit the current conversation. Moving the request off the speech path only solves half the problem; accepting its result needs a state-management policy.

The implementation coalesces background work and validates a result against the transcript snapshot it actually read. New turns can extend an unchanged source prefix without invalidating that work. Rewritten or removed source turns, or a result that would rewind already-processed progress, cause rejection. Accepted context is committed for later turns instead of forcing the speaker to wait for every analysis pass.

A provider-stubbed regression test deliberately holds the analysis response open while the speech path completes. That checks a concrete architectural property: routine speech does not depend on completion of the slow request. It does not measure the full delay a caller hears. Provider inference, transport, synthesis, and playback need separate evidence.

Design for failure, maintenance, and recovery

The AWS implementation runs a Node voice backend behind an HTTPS load balancer, with ECS Fargate and private PostgreSQL storage. An actor abstraction preserves the conversation handlers while moving state and scheduled work into database-backed records. State changes and alarms commit together; interrupted alarms can be retried, and an uncertain call-creation attempt is retained for reconciliation instead of triggering a duplicate call.

The initial runtime deliberately uses one active process. A database advisory lock owns that boundary. Losing the lock connection removes readiness, stops scheduling, and closes WebSockets. Durable state helps recovery, but cannot restore an interrupted telephone connection. The tradeoff is explicit: this version needs drained deployments and cannot gain safe horizontal scaling merely by increasing the task count.

The release workflow builds an immutable staging image and promotes the same tested digest to production. It requires calls to be drained and checks runtime readiness; deploying an image does not silently enable calling. Operational logging is limited to metadata, while conversation artifacts follow a separate access boundary. Alert delivery, restore timing, and provider reconnection still need environment-specific rehearsal evidence.

The finalized-call integration adds a transactional outbox, queue-based processing, private artifact storage, and retried callbacks toward Workflows. Those mechanisms address duplicate events and temporary downstream failure. Their presence in source does not activate a particular tenant, patient workflow, or clinical data path.

Tool results and deterministic action boundaries

“You’re booked” is a consequential claim. The model’s sentence cannot establish that an action succeeded. For booking and availability tools, the fast loop withholds the draft text, executes the tool through the runtime, and requests a response informed by the committed result. This trades an additional model round for control over the order of action and speech; it does not guarantee the semantic truth of every generated sentence.

The executor rechecks the active socket, response identity, session state, calling gate, and recipient authorization before applying a tool effect. A delayed response from an interrupted turn cannot inherit authority from the current one. Synthetic booking also rejects a slot that was not offered. These are application controls, separate from the model’s judgment about what the caller intended.

Final extraction has its own evidence boundary. A confirmed booking in the brief comes from a successful tool result, even if the transcript sounds confident. Structured output must pass schema checks; transcript references must resolve, and quoted concerns must match their cited turns. Supplied chart context remains unverified input. Evidence pointers establish provenance, while clinical meaning and conversational appropriateness still require evaluation.

Consent is part of that evaluation: scenarios check that Sally does not substitute an unchosen appointment, treat an instruction override as permission to book, or claim an action that never occurred. Recipient identity and authority are distinct requirements, enforced outside the LLM. The current source requires AI disclosure and verification before protected context, model conversation, or actions. The reviewed adapter defaults to denial when an approved verification policy is unavailable; its fallback is a neutral introduction and safe termination. Enabling a different policy is a release and authorization decision, not a prompt change.

Engineering AI Reliability: Evaluations, Regression Testing, and Model Selection

I approach reliability as a set of testable boundaries. A deterministic test can establish that stale work is rejected. It cannot establish that a live model will ask an appropriate follow-up question. The evaluation strategy needs both, with a clear account of what each result proves.

Deterministic tests for state and evidence

Provider-stubbed tests control timing and outputs so failures are reproducible. They cover speech completing while analysis is pending, rejected stale context, delayed tool requests after interruption or reconnect, closed sessions, and disabled calling. Extraction tests deliberately supply bad references, drifting quotations, and a transcript that claims a booking without a successful tool result.

These tests protect implementation contracts. Their passing result says nothing by itself about live-model quality, telephone latency, clinical outcomes, or production reliability.

Scenario regressions and fixed-turn model comparisons

Separate live-model evaluations use defined scenarios and expected behavior: an unavailable appointment, a caller-selected slot, an attempted instruction override, or a question about whether Sally is human. Tool assertions and behavioral rubrics make regressions inspectable as prompts, adapters, and models change. The synthetic continuity screen also records when accepted background context became available and whether later turns used it.

For speaking-model comparisons, a fixed-turn replay freezes the conversation up to one caller turn and asks each candidate for the next response. This makes the input comparable without pretending the rest of the conversation would remain unchanged. Once a candidate says something different, the caller might answer differently too. Replaying the original caller’s later words would test an artificial continuation.

Debugging the evaluator before changing the model

An unavailable-slot scenario failed because the injected context did not say that the offered slots were the complete availability for that call. The documented fix clarified the mutable booking context and left the frozen speaking prompt unchanged. The finding pointed to missing information, not a need to rewrite the model’s personality.

Another screen ran a synthetic conversation so quickly that background analysis arrived after the scored turns. Its gate partly rewarded a slower speaker. The revised harness makes turn pacing explicit, reports when memory arrives, and checks that a started analysis produces an accepted update. Adding a blocking analysis step to every turn would have addressed a test artifact at the expense of the architecture.

Evaluation artifacts make those distinctions reviewable. The continuity screen retains scenario and source identifiers, fixture and prompt hashes, provider rounds, speech, tool activity, timing spans, and mechanical failures. It marks semantic review as pending rather than treating a mechanically clean run as a quality verdict. Failures, incomplete runs, and configuration belong alongside favorable results.

Those investigations shape my model-selection decisions: identify the failed behavior, inspect the context the model received, and check whether the evaluator represents the workload. A larger model or longer prompt is useful only when it addresses the demonstrated cause. I keep speaking, analysis, and extraction evidence separate instead of declaring one model the winner for the whole system.

Why these boundaries matter in healthcare

The workflow needs a conversation that stays responsive while preserving a useful record for the care team. Background context can support continuity; transcript-grounded extraction can make visit briefs easier to inspect; tool evidence can reduce unsupported claims about completed actions. Deterministic authorization limits when the application may act at all.

My responsibility is to preserve that separation through integration and operation: patient statements, verified records, consent, and completed actions must remain distinguishable. The mechanisms support reliability and reviewability; they do not by themselves measure clinical benefit or staff time saved.

Track capability at the integration and release boundary

Sally’s production engineering spans conversation orchestration, background context, transport integration, persistent state, evidence processing, and release controls. The separate scheduling sales presentation is prerecorded and does not place calls or book appointments. It demonstrates a journey, while the interactive runtime and its enabled integrations require their own operational evidence.

The reviewed source does not establish an active production recipient-verification adapter, live EHR scheduling, or completed rollout of the Workflows callback path. Those specific integration claims need the matching deployment and acceptance record. Synthetic test results remain valuable regression evidence without becoming appointment, adoption, or clinical-outcome metrics.
